## Product Truth After the Simplification

Hermes Flywheel should be a compact, local-first planning and verification plugin, not a hidden worker runtime.

Core principles:

- local-first and stdlib-only
- tools are authoritative for state transitions
- evidence gates remain non-negotiable
- no background execution substrate inside normal plugin tool handling
- no hidden network calls
- no git mutation from plugin tools
- no task completion without explicit completion evidence
- optional integrations should be external adapters, not baked-in worker state

The deleted v0.5-v0.7 machinery is now explicitly considered obsolete in this codebase unless Kevin reverses that decision.

# Revised Parity Strategy

The previous v0.8-v1.0 plan assumed the worker/assignment/handoff path continued. Kevin’s latest changes reverse that direction. So parity should now mean “Hermes-native orchestration leverage,” not “clone the previous worker substrate.”

## New Interpretation of Parity

Parity should be measured by user outcome:

1. Understand repo state.
2. Produce a plan.
3. Track tasks and dependencies.
4. Advance work in evidence-gated waves.
5. Verify completion evidence.
6. Diagnose state corruption or incomplete work.
7. Recover/resume safely.
8. Optionally hand off execution to external systems without hiding side effects.

This can be achieved without internal worker records.

# v0.9: External Handoff Export, Not Worker Runtime

## Goal

Replace the deleted internal handoff subsystem with a simpler export contract for external agents/humans.

## Product Consequence

Hermes Flywheel can produce task packets for external execution without owning worker lifecycle.

## Proposed Tool

### `hermes_flywheel_export_wave`

Read-only or write-explicit export of a started/ready wave.

Inputs:

- `cwd?: string`
- `wave_id?: string`
- `format?: "json" | "markdown"`
- `output_path?: string`
- `include_evidence_contract?: boolean`

Behavior:

- Selects a ready/started wave.
- Exports task specs, dependency context, evidence requirements, and verification instructions.
- Does not create worker state.
- Does not mark tasks done.
- Does not create completion evidence.
- If writing `output_path`, path must stay inside project root or `.hermes-flywheel/exports/`.

State addition, if any:

- `exports: []`
- `export_events: []`

But prefer no state at first unless there is a clear resume need.

## Why This Instead of Restoring Handoffs

The deleted handoff system was too close to becoming a parallel worker runtime. Export packets give us the useful half — precise execution instructions — without owning worker lifecycle.

# v1.0: Adapter Documentation + Read-Only Integration Status

## Goal

Define how external systems integrate with the lean core without adding hidden execution.

## Product Consequence

The plugin reaches “parity enough” by being a reliable planning/verification nucleus that other systems can drive.

## Proposed Additions

- Document external integration patterns:
  - Hermes subagents
  - GitHub Issues
  - Beads
  - Agent Mail
  - Linear
  - manual CLI/human execution
- Add optional import/export helpers only where they are local and explicit.
- Add `hermes_flywheel_status` as the v1.0 hook: a read-only supervisor summary of local state, task/wave counts, active incomplete started wave, exportable wave, checkpoint health, and suggested next tool.
- Keep imports out of scope for v1.0 unless a concrete local-only report format is needed; completion reports already enter through `hermes_flywheel_review`.

## No Hidden Runtime Rule

v1.0 should still not spawn workers from plugin tools. Execution belongs to Hermes itself, subagents, or external orchestrators — not the plugin’s core tool handlers.

Strong Hermes-native parity: v1.0 completes the smallest strong slice by pairing v0.9 exports with read-only supervisor status and explicit adapter documentation. External orchestrators can now inspect next action, export work, submit completion reports, verify evidence, and checkpoint without the plugin owning execution.

# How Many More Versions Are Needed?

Given Kevin’s simplification, estimate from the new baseline:

## Lean-core parity: 2 more versions

- v0.8: stabilize simplified lean core after deleting worker/assignment/handoff substrate
- v0.9: export wave/task packets for external execution

At this point the plugin is useful and coherent: plan, wave, verify, checkpoint, doctor, export.

## Strong Hermes-native parity: 3 more versions

- v0.8: lean-core stabilization
- v0.9: external export contract
- v1.0: integration docs/hooks/status for external orchestration

Call v1.0 “parity enough” if it can:

1. profile a repo
2. plan work
3. create/update tasks
4. advance evidence-gated waves
5. export wave/task instructions for external execution
6. accept completion reports
7. verify evidence
8. checkpoint/recover state
9. diagnose/remediate local state safely

## Full original-style parity: no longer recommended

Rebuilding the removed worker/assignment/handoff substrate would take roughly 4-6 more versions, but that now appears to be the wrong bet for this repo.

If full original-style parity is desired anyway, the old sequence would be:

- worker substrate
- assignment substrate
- handoff packets
- handoff verification/readback
- runtime adapter interface
- supervised local execution

But Kevin just removed the first three. Treat that as product signal: keep the core small and let Hermes/external systems execute.
